# S0: Interop and render loop

Spike S0 ([08 §3](../08-implementation-plan.md#s0--interop-and-render-loop-inside-m1)) asks one question. Can Blazor WebAssembly on .NET 10 drive 20 cars at 60 fps with the planned interop pattern? It also measures the download and checks how the app's files are served from GitHub Pages. Tracked in [#13](https://github.com/jbird/race-replay/issues/13).

> **Status:** done. Frame rate, AOT, the chart path, scrubbing and Brotli decoding are measured in Chrome 155 and Firefox 157, in visible windows on Claude's machine (see [Browser measurements](#browser-measurements)). That is a 2015 desktop, slower per core than a current mid-range laptop, so the numbers are conservative. Safari is not measured: there is no Mac. **The exit is met:** both browsers hold 60 fps on the public Release build, with .NET work at 0.3–0.5 ms per frame.

## Setup

- **Replay:** synthetic seed 1 (Corrie Motor Circuit). 20 cars, 17,166 samples at 4 Hz (1:11:31).
- **Builds:**
  - **Release:** `dotnet publish -c Release`, trimmed, with the interpreter and jiterpreter (no AOT).
  - **Debug:** `dotnet run` with the dev server.
  - **AOT:** `-p:RunAOTCompilation=true`.
- **Instrument:** the `?perf` hook in `renderLoop.js` (see [CONTRIBUTING](../../CONTRIBUTING.md#measuring-frame-rate)). It reports 10 s windows:
  - the frame interval;
  - the time inside `OnFrame`, split into canvas drawing (timed in `trackMap.js`) and the rest, called **.NET**. That is the clock, sampling, interop, view-state publishes and the Blazor re-renders they trigger.
- **Claude's machine:** Intel Core i5-6600K (4 cores, 3.5 GHz, 2015), 16 GB, GeForce GTX 1060, Windows 10, one 3840 × 2160 monitor at 60 Hz. It is slower per core than a current mid-range laptop, so its numbers are conservative.
  - **Chromium pane:** the Claude desktop app's built-in Chromium 152 pane, at devicePixelRatio 2. It throttles: it runs at 60 fps while visible and about 30 fps when hidden, so its fps figures are indicative only. Per-frame work times are steady across runs.
  - **Chrome 155 and Firefox 157:** visible 1400 × 1000 windows at devicePixelRatio 2 (a page of about 1390 × 910 CSS px), with throwaway profiles. Claude drove them as in [S2](S2.md#chrome-on-claudes-machine): Chrome over its DevTools protocol, Firefox over WebDriver BiDi. Occlusion tracking was off (Chrome's `--disable-backgrounding-occluded-windows`, Firefox's `widget.windows.window_occlusion_tracking.enabled`), and every run checked that the page was visible and focused.
  - **Safari:** not measured: there is no Mac.
- **Timer resolution:** `performance.now()` is coarsened to 0.1 ms in Chrome and about 1 ms in Firefox (no cross-origin isolation on Pages). Turning off `privacy.reduceTimerPrecision` doesn't change Firefox's. Compare **means** in Firefox.

|---|---|---|---|---|
| Release | 30.0 (pane hidden) | 1.19 / 0.6 / 3.4 | 0.33 / 0.3 / 0.7 | 0.87 / 0.2 / 3.0 / 9.8 |

- **A typical frame is cheap.** .NET p50 is 0.2–0.4 ms and canvas p50 0.3–0.4 ms. That is well inside the 05 §11 budgets (`Advance` + `Sample` < 0.1 ms, interop < 0.05 ms, canvas < 3 ms) and the exit's "< 1 ms of .NET work per frame".
- **The p95 comes from the view-state frames.** At 10 Hz, `UiPublisher` publishes and Blazor re-renders `PlaybackControls` and `Scrubber` synchronously inside `OnFrame`, which costs about 3–6 ms on those frames. That is at the edge of the 05 §11 "Blazor re-render < 4 ms" budget, but well inside a 16.7 ms frame.
- **Debug is no slower than Release here.** The interpreter does the same work either way, and the difference is within noise in the pane.
- **AOT trims the slow frames rather than the typical one.** .NET mean is 0.63 ms against 0.87 ms, p95 2.6 against 3.0 ms, and max 4.6 against 9.8 ms. The p50 is unchanged at 0.2 ms.

### Interop

- **`Span<double>` → `[JSMarshalAs<JSType.MemoryView>]` works on .NET 10.** The frame crosses without a copy, and `trackMap.js` copies it into a reused `Float64Array` with `copyTo`. A MemoryView has no `get(i)`; 05 §5.4 was corrected in #57.
- **Two interop transitions per frame:** `OnFrame` in and `DrawCars` out. There is no `SetCursor` until the gap chart arrives (#32).
- **Fingerprinted JS modules resolve through the import map.** With `<StaticWebAssetFingerprintPattern Include="JSModule" Pattern="*.js" Expression="#[.{fingerprint}]!" />`, the build:
  - lists `./js/renderLoop.js` → `./js/renderLoop.{fingerprint}.js` in the import map;
  - publishes only the fingerprinted files.

  `JSHost.ImportAsync(..., "../js/renderLoop.js")` then loads the fingerprinted module, in a local publish and on the dev server. So does the static `import … from './trackMap.js'` inside `renderLoop.js`, which gets the same module instance.

### Gap-chart path (uPlot, throwaway branch `spike/s0-chart`)

A `/spike/chart` page imports a module that imports vendored uPlot 1.6.32, the way `gapChart.js` will in M5. It draws 20 series × 7,200 points with the y axis inverted and data holes, then moves a cursor overlay every frame with `transform: translateX(…)`. Debug dev server, Chromium pane:

| Step | Time |
|---|---|
| Build and first draw | 23.6 ms |
| Full redraw on resize, timed until uPlot's `draw` hook | ~16.6 ms, an upper bound that includes waiting for the next frame |
| Cursor move per frame (style write) | p50 < 0.1 ms, p95 0.1 ms, max 0.2 ms |

Chrome 155 and Firefox 157 (Claude, 17 October 2026, [Setup](#setup)): a Release publish of the branch, served by `python -m http.server`. Chrome opened the page nine times and Firefox seven: first loads after the browser started, later loads, and return visits within the app.

| Step | Chrome 155 | Firefox 157 |
|---|---|---|
| Build and first draw | 32–36 ms on the first load, 20–24 ms after | 29–32 ms on the first load, 22–26 ms after |
| Full redraw on resize | 13–20 ms | 17–22 ms |
| Cursor move per frame (style write) | p50 < 0.1 ms, p95 0.1–0.3 ms, max 0.6–1.9 ms | p50 0, p95 0–1 ms, max 1–3 ms (1 ms clock) |
| Cursor loop over 10 s | 58.2–58.8 fps, 2 frames over 20 ms | 57.5–58.5 fps, 1–2 frames over 20 ms |

- **A redraw is synchronous work, about one frame.** A frame watcher saw no frame between the build and the two redraws, so the pane's ~16.6 ms was real drawing time, not mostly a wait for the next frame.
- **Each build is followed by one long frame:** 167–217 ms in Chrome and 300–450 ms in Firefox. After it, the cursor loop holds 60 fps, but the long frame is what pulls the 10 s figure under 60.
  - It comes back when the page is opened again within the app, so it isn't a first-load cost.
  - Chrome's Long Animation Frames API shows no rendering and no script over 5 ms in that frame, so it isn't uPlot drawing or the cursor.
- **Drawing the chart once per load or mode change, as 05 §4.4 plans, is affordable, but not during playback.** A build or a redraw blocks a frame or more, and the long frame after a build would show as a skip. #32 (RR-060) should build and resize the chart while paused or behind the loading overlay, and check whether the long frame remains with the real chart.
- **Moving the cursor per frame is essentially free**, so `SetCursor` stays a one-number interop call.
- **Fingerprinting applies to every `*.js` under `wwwroot`, vendored libraries included.** They must be loaded as ES modules through the app's import map (a relative `import` from a module, or `JSHost.ImportAsync`), not with a plain `<script src>` or from a separate HTML page. uPlot's ESM build (`uPlot.esm.js`) works this way, and M5 should vendor that build.

### GitHub Pages

Checked with `curl` against https://jbird.github.io/race-replay/ on 15 October 2026.

- **Compression:** Pages gzips every file it serves when the request asks for `gzip`: the app (`.wasm`, `.js`, `.css`, `.html`), JSON, and the `application/octet-stream` bundle files. It never sends Brotli: a request accepting only `br` gets the uncompressed file. Browsers send `gzip, deflate, br`, so they get gzip. A demo race costs 1.26–1.50 MB over the wire:

  | File | Raw | gzip from Pages |
  |---|---|---|
  | `catalog.json` (all three races) | 542 B | 272 B |
  | Seed 1 `manifest.json` / `positions.rrb` | 6,180 B / 1,417,504 B | 2,623 B / 1,260,855 B (−11 %) |
  | Seed 3 `manifest.json` / `positions.rrb` | 7,062 B / 1,664,224 B | 2,954 B / 1,496,555 B (−10 %) |
  | Seed 7 `manifest.json` / `positions.rrb` | 6,162 B / 1,486,464 B | 2,635 B / 1,379,031 B (−7 %) |

  The quantised positions barely compress as they are, which is input for S2's delta-encoding option (#15). The browser decodes the gzip transparently, so `HttpReplaySource` still receives the manifest's byte count.
- **The pre-built `.br` copies are deployed** and served as plain files (`200`), so `loadBootResource` can fetch them.
- **Caching:** every file is `Cache-Control: max-age=600`, which is why the JS modules are now fingerprinted.
- **Deep links:** `/race-replay/replay/demo/1?t=600` returns `404` with the `index.html` body (the `404.html` copy), and the app routes client-side, as 05 §12.1 expects.

### Scrubbing in Chrome and Firefox

NFR-02 asks that a seek render the new frame within one animation frame. Claude, 17 October 2026, on the public site in the visible windows of [Setup](#setup). During 1× playback of seed 1 with `?perf`, the harness pressed the scrubber (`pointerdown`). Then, between every two frames, it set a random position and fired `input`, about 1,500 seeks in 25 s, and finally released it (`pointerup`, `change`). Blazor handles `input` synchronously, so its dispatch time is the seek plus any re-render. Four runs in Chrome (two position sequences) and two in Firefox.

| | Chrome 155 | Firefox 157 |
|---|---|---|
| Seek (`input` dispatch) mean / p50 / p95 | 0.78–0.85 / 0.7 / 1.4–1.5 ms | 0.92–0.94 / 1 / 2 ms |
| Seeks over 8 ms | 2–3 per run, 11–50 ms | 3 per run, 11–55 ms |
| While scrubbing, per 10 s window | 59.6–60.0 fps, 0–2 frames over 20 ms | 59.7–59.9 fps, 1–2 frames over 20 ms |

- **Seeking is instant.** A seek takes under 1 ms on average and 1.4–2 ms at p95, well inside a frame, so the next frame shows the new position. Dragging paused playback, and releasing resumed it, in both browsers.
- **The slow seeks are warm-up.** They fall on the same seek numbers, 330, 498 and 998, in both browsers, and in Chrome with a second sequence of positions too. So they depend on how many seeks have run, not on where they go, most likely the runtime optimising hot code after a set number of calls. Each costs up to three frames, once per session.

### Decoding the framework in the browser (`loadBootResource`)

A throwaway page set `autostart="false"` and called `Blazor.start({ loadBootResource })`, fetching `defaultUri + '.br'` or `'.gz'` for every boot resource except `dotnetjs` and `configuration`. It was served from a local static server with no compression, using the local Release publish.

- **It works with .NET 10 fingerprinted names.** All 39 resources loaded through it, the integrity checks passed on the decoded bytes, and the app ran.
- **Chrome 152's `DecompressionStream` has no `brotli` format**, so Brotli needs a JS decoder. `gzip` works natively, but Pages already gzips.
- **Brotli with google/brotli `decode.min.js` (MIT):** 1.63 MB fetched instead of 1.99 MB as gzip. Decoding is synchronous on the main thread: 137 ms in total, 50 ms for the largest file. The decoder itself is 151 KB, 67 KB gzipped.
- **Net saving on this build:** about 0.3 MB over the wire, for about 0.14 s of main-thread decoding on this machine.

Chrome 155 and Firefox 157 (Claude, 17 October 2026, [Setup](#setup)), with the `s0-boot.js` recipe under [Browser measurements](#browser-measurements). It ran on a local Release publish (39 resources: 1.63 MB of Brotli, 4.93 MB decoded), served by `python -m http.server` with the browser cache off. Eight page loads in Chrome and nine in Firefox. Each rendered the catalogue with no error.

| | Chrome 155 | Firefox 157 |
|---|---|---|
| Main-thread decode, all 39 files | 124–155 ms, median 134 ms | 158–178 ms, median 169 ms |
| Largest single file (`dotnet.native.wasm` or `System.Private.CoreLib.wasm`) | 31–53 ms | 57–76 ms |
| `DecompressionStream('brotli')` | Not supported | Supported: the 39 files decode in 51–104 ms, one after another |

- **The decode costs more time than it saves at 50 Mbit/s.** Net of the 67 KB decoder, Brotli saves about 0.29 MB over gzip. At NFR-03's 50 Mbit/s that is under 50 ms of download, against 124–178 ms of decoding here. Ignoring any overlap with the downloads, it breaks even only below about 15 Mbit/s. A laptop twice as fast per core would still lose at 50 Mbit/s.
- **Firefox 157 decodes Brotli natively; Chrome 155 doesn't.** Once Chrome supports `DecompressionStream('brotli')`, there is no decoder to ship and no JS decode on the main thread.

## Decisions

1. **Frame path: keep `Span<double>` → `MemoryView`.** No fallback to `double[]` is needed.
2. **JS modules: fingerprint them through the import map.** This is enabled in `RaceReplay.Web.csproj`, so no `?v=` query is needed.
3. **The view-state re-render stays inside the frame for now.** It fits the frame budget. If the timing tower (#33) pushes publish frames past about 8 ms, the levers are:
   - render less, with `ShouldRender` or only the changed parts;
   - publish outside the `requestAnimationFrame` callback;
   - lower `UiRefreshHz`;
   - AOT.
4. **AOT (input to Q4 and #43): not now.** In Chrome it trims the slow frames: .NET p95 drops from 1.1–2.9 ms to 0.7–1.2 ms and the slowest frame from 5–11 ms to 1.2–2.5 ms, while the mean moves from 0.35–0.69 ms to 0.24–0.36 ms. But it makes the framework 2.7× larger over the wire (5.68 MB against 2.13 MB gzip), which breaks the 3 MB budget (05 §11, NFR-03). The interpreter already holds 60 fps in Chrome and Firefox here. #43 revisits this with the timing tower and gap chart in place.
5. **Download (for #37 and S2, #15):**
   - **Relinking the native runtime in CI** is the bigger, cheaper win. Install the `wasm-tools` workload in the `publish-site` and deploy jobs; it saves about 0.6 MB over the wire with no runtime cost.
   - **In-browser Brotli: not now (input to RR-070, #37).** It works with fingerprinted names, but the JS decoder takes 124–155 ms of main-thread time in Chrome and 158–178 ms in Firefox here, to save about 0.29 MB net of the 67 KB decoder. That is under 50 ms at 50 Mbit/s. Firefox 157 already decodes Brotli natively with `DecompressionStream('brotli')`. Revisit when Chrome does too.

**Brotli decode cost.** The question is the main-thread time to decode the framework, which decides whether #37 decodes Brotli in the browser. It takes 124–155 ms in Chrome and 158–178 ms in Firefox on Claude's machine.

1. In the `artifacts/s0-aot` copy above, or any Release publish, download [`decode.min.js`](https://github.com/google/brotli/blob/v1.1.0/js/decode.min.js) into `wwwroot/lib-brotli/`.
2. In `wwwroot/index.html`, add `autostart="false"` to the `blazor.webassembly…js` script tag, and add `<script type="module" src="s0-boot.js"></script>` after it.
3. Save this as `wwwroot/s0-boot.js`, open the site, and read `__s0` in the console:

```js
import { BrotliDecode } from './lib-brotli/decode.min.js';

const started = performance.now();
const loaded = [];
globalThis.__s0 = { loaded };
Blazor.start({
  loadBootResource(type, name, defaultUri) {
    if (type === 'dotnetjs' || type === 'configuration') return;
    return (async () => {
      const compressed = await (await fetch(defaultUri + '.br', { cache: 'no-cache' })).arrayBuffer();
      const begin = performance.now();
      const decoded = BrotliDecode(new Int8Array(compressed));
      loaded.push({ name, ms: performance.now() - begin });
      return new Response(decoded, { headers: { 'content-type': type === 'dotnetwasm' ? 'application/wasm' : 'application/octet-stream' } });
    })();
  },
}).then(() => {
  __s0.bootMs = performance.now() - started;
  __s0.decodeMs = loaded.reduce((sum, l) => sum + l.ms, 0);
  console.info(__s0);
});
```

**Exit (08 §3):** sustained 60 fps in Release in at least Chrome and Firefox, and .NET work under 1 ms per frame, met at the mean and p50.

**Result: met on Claude's machine.** On the public Release build, Chrome held 60.0 fps with no frame over 20 ms in every full window. Firefox did in 11 of 12, and its one slower window (58.6 fps) came from outside the app's frame. .NET work averaged 0.29–0.35 ms per frame in Chrome and 0.32–0.53 ms in Firefox, with a p50 of 0.1–0.2 ms in Chrome. No lever and no ADR-0003 addendum is needed. If a slower machine misses it, apply the levers in [05 §11](../05-web-client.md#11-performance-budget) in order, and add an addendum to [ADR-0003](../adr/0003-blazor-webassembly-with-thin-js.md).
