# S2: Packaging and hosting

Spike S2 ([08 §3](../08-implementation-plan.md#s2--packaging-and-hosting--05-day-after-m1)) asks whether local packages and hosted bundles work well in the browser, at the smallest transfer for acceptable complexity (Q3). It decides how hosted bundles are stored (option A, B, C or D, [04 §9](../04-data-pipeline-and-bundle-format.md#9-compression-and-hosting-spike-s2)) and whether package entries are stored or deflated. Tracked in [#15](https://github.com/jbird/race-replay/issues/15), where the acceptance criteria are.

> **Status:** measured by Claude, apart from Chrome on a laptop (and Safari). Sizes, the fit to Pages' gzip, decode times, package opening and memory are done. The browser numbers come from the app's Chromium pane (indicative) and from [Firefox 157](#firefox-on-claudes-machine), both on Claude's machine, a 2015 desktop. Still to come: Chrome on a mid-range laptop, and Safari if you have a Mac (see [your measurements](#your-measurements)). The [reading so far](#reading-so-far) holds unless those numbers change it.

## Setup

- **Builds:** `scripts/s2-variants.cs`, a .NET 10 file-based app, run with `dotnet run scripts/s2-variants.cs`. It takes about 70 s.
  - Synthetic seed 1 (Corrie Motor Circuit), 20 cars, built through the real `ReplayBuilder` and `ReplayBundleWriter` onto the 4 Hz timeline.
  - Lap counts come from a linear fit of samples against laps: 265.6 samples per lap plus 626 of overhead.
  - **Stand-in progress:** M2 derives the real channel. Until then, each car's progress is its cumulative distance travelled along its own X/Y, in track units, as Float32. It is monotonic and smooth like the real channel, so it should compress like it.
  - The build time is fixed, so two runs write byte-identical files. The script prints a SHA-256 for every file, and two runs print identical output.
  - Output goes to the gitignored `artifacts/s2/`. Nothing it writes is committed.
- **Variants** of the 2-hour `positions.rrb`, all the same length as the raw file:
  - **raw:** schema 1.0, as written today;
  - **delta:** X and Y as differences from the previous sample, wrapping in 16 bits, with flag bit 0 set (04 §7.3);
  - **delta-qprogress:** as delta, plus progress rounded to whole track units and stored as Int32 differences (a candidate encoding, id 4). Invalid samples hold the last valid value, as the writer already does for X and Y.

  The script checks each file's magic, version and kind before it parses, since it restates the layout that the Bundle project keeps internal. It then decodes each variant and checks it against the raw file: X and Y exactly, valid progress samples within half a track unit, and every byte outside the channel blocks (header, directory and padding) except the flags and the changed encodings.
- **Packages:** `.rrz` files with the 04 §7.1 entries (`manifest.json`, `positions.rrb`, `DATA-NOTICE.txt`), written once with stored entries and once deflated (`CompressionLevel.Optimal`). Each is read back with `ZipArchive` and `ReplayBundleReader`. There is no `gaps.rrb` yet.
- **Compressors:**
  - "gzip *n*" with **classic zlib** is GNU gzip 1.14 (`gzip -n -<level>`), used to predict Pages;
  - "gzip *n*" with **zlib-ng** is .NET 10's `GZipStream` with `ZLibCompressionOptions`, which is what the CLI would write for option B or C;
  - Brotli is .NET's `BrotliEncoder`, quality 11, window 22. Pages never sends Brotli, so it is for reference only.
- **Browser:** two throwaway pages on the unmerged branch `spike/s2-browser`, linked from its catalogue page.
  - `/spike/decode` fetches the variants' `.rrb.gz` files, then times each decode once cold and five times warm (median).
  - `/spike/package` opens a `.rrz` the way [05 §9.2](../05-web-client.md#92-from-the-users-disk-localpackagereplaysource-real-races) plans: `InputFile` → `OpenReadStream(64 MB)` → `MemoryStream` → `ZipArchive` → `ReplayBundleReader` → `ReplaySessionHost.Open` → the first frame. It can also hand the bytes over with `File.arrayBuffer()` and `[JSImport]`. It shows each step's time and the WebAssembly memory after the load.
  - **Build:** `dotnet publish -c Release`, trimmed, interpreter and jiterpreter, native relinked locally. Served by `python -m http.server` without compression, so no timing includes a transfer.
  - **Claude's machine:** as in [S0](S0.md#setup): Intel Core i5-6600K, Windows 10, the Claude desktop app's Chromium 152 pane.
  - The pane was hidden, which pauses `requestAnimationFrame`. So the page draws the first frame by calling the exported `OnFrame`, as the loop's first tick would. A visible page adds up to one vsync (16.7 ms).
  - Package files went to `InputFile` through a `DataTransfer`, from a `Blob` in memory. So "read" covers the hand-over to .NET but no disk read.
  - "Cold" is the first run after a fresh page load. The first open of a package happens cold, so that is the number for NFR-03.

### Pages' gzip

Checked with `curl` against https://jbird.github.io/race-replay/ on 16 October 2026. Each demo file was fetched twice: without `Accept-Encoding` for the exact deployed bytes, and with `Accept-Encoding: gzip`.

| File | Raw | Pages | Classic gzip 5 | Difference |
|---|---:|---:|---:|---:|
| Seed 1 `positions.rrb` | 1,417,504 | 1,260,855 | 1,263,778 | −0.23 % |
| Seed 3 `positions.rrb` | 1,664,224 | 1,496,555 | 1,500,466 | −0.26 % |
| Seed 7 `positions.rrb` | 1,486,464 | 1,379,031 | 1,378,821 | +0.02 % |
| Seed 1 `manifest.json` | 6,180 | 2,622 | 2,621 | +1 B |
| Seed 3 `manifest.json` | 7,061 | 2,956 | 2,956 | 0 B |
| Seed 7 `manifest.json` | 6,162 | 2,635 | 2,636 | −1 B |

- **Pages behaves like classic zlib at level 5.** The compressible manifests separate the levels best. Level 5 matches all three to a byte, level 4 is about 1 % larger, and levels 6–9 differ by up to 0.25 %. No level is byte-identical, so Pages' compressor isn't exactly GNU gzip, but the sizes agree to within 0.3 %.
- zlib-ng (.NET) fits worse. Its level 9 comes within 1–5 bytes on the manifests, but it is about 1 % smaller than Pages on the `.rrb` files (1,248,599 B against 1,260,855 B for seed 1), where classic level 5 is within 0.26 %.
- Responses carry `Content-Encoding: gzip` and `Content-Type: application/octet-stream`, from Fastly (`Via: 1.1 varnish`).

So a variant's transfer from Pages is predicted by classic gzip 5, give or take 0.3 %.

### Where the bytes are

All cars' blocks of each channel, concatenated in file order, bytes:

| Channel | Raw | gzip 9, raw | gzip 9, delta | gzip 9, delta-qprogress |
|---|---:|---:|---:|---:|
| X | 1,135,480 | 1,058,095 | 631,642 | 631,642 |
| Y | 1,135,480 | 952,934 | 653,028 | 653,028 |
| Progress | 2,270,960 | 1,871,521 | 1,871,521 | **380,505** |
| Validity | 70,980 | 203 | 203 | 203 |

- **Progress is half the file and nearly half the compressed size.** Float32 mantissas barely compress (−18 %). As whole track units, delta-encoded, it shrinks to 0.38 MB, a fifth.
- Delta encoding cuts X and Y by 30–40 % after gzip.
- Rounding progress to a track unit (0.1 m) loses nothing that matters. Float32 already resolves only about 0.5 units at 5,000,000 units, the end of a 2-hour race. At 80 m/s, 0.1 m is 1.25 ms of gap.

### Decode times in the browser

Claude, Chromium pane, Release, two fresh page loads. Times in ms as cold / warm median, with the range over the two loads.

| Variant | `.gz` bytes | `GZipStream` (.NET) | `DecompressionStream` (JS) | JS → .NET hand-over | Delta prefix sums |
|---|---:|---:|---:|---:|---:|
| raw | 3,922,850 | 39–51 / 32 | 38–40 / 36 | 3–5 / 2–3 | – |
| delta | 3,227,353 | 30–63 / 25 | 32–36 / 31–32 | 2 / 1 | 17–18 / 7–8 |
| delta-qprogress | 1,770,782 | 19–20 / 18 | 21–22 / 22 | 2 / 1 | 10–11 / 11–12 |

`ReplayBundleReader.Read` on the raw 2-hour bundle (parse, checks, dequantise): **119–157 ms cold**, 49 ms warm.

- **.NET's `GZipStream` works on browser-wasm and is as fast as the browser's `DecompressionStream`.** zlib runs as native WebAssembly inside the runtime, while the JS path pays a copy back into .NET. Option B or C would need no JS helper.
- **Inflating costs 8–10 ms per compressed MB.** That is 18–20 ms for delta-qprogress.
- **The delta prefix sums cost 7–18 ms** over the whole 2-hour file. In the real reader they would fold into the dequantise pass, which already walks every value.
- **With option D, .NET does no inflating.** The browser inflates the response natively as it arrives, so .NET pays only the prefix sums.
- The bundle reader's cold run is 2.4–3.2 times its warm one, and above the 20–50 ms that [05 §9.1](../05-web-client.md#91-from-the-site-httpreplaysource-demo-and-hosted-races) expects. It is the largest .NET step in every load below.

### NFR-03 for a hosted 2-hour bundle

First paint must come within 5 s on a 50 Mbit/s connection with a cold cache. The app is about 2.73 MB over the wire as Pages serves it now: 2.58 MB of `_framework/*.wasm` (S0), plus about 0.15 MB of JS, CSS and HTML (`dotnet.runtime.js` 57 KB, `dotnet.native.js` 52 KB, `blazor.webassembly.js` 19 KB, `dotnet.js` 15 KB, the rest under 4 KB each, gzipped). ## Reading so far

These become the decisions, and the ADR-0004 addendum, once your laptop numbers are in.

1. **Hosted bundles: option D, with quantised progress.** By #15's rule, the simplest option that meets NFR-04 wins.
   - A and B miss NFR-04 by about 1 MB.
   - D needs only prefix sums at load (about 10 ms) and no decompression code, and Pages' gzip takes it to 1.93 MB.
   - C is 8 % smaller than D, short of the 15 % that would justify a decompression path, and it costs another 18–20 ms of inflating.
2. **Format:** delta X/Y and quantised progress look worth putting into the format in M4 (#28–#30), before golden bytes are fixed. Progress quantisation does most of the work: 1.35 MB of the 2.05 MB saved over the wire, so it matters more than delta on X/Y.
   - **Neither is a minor-version change.** Both change what existing channel bytes mean, and [04 §10](../04-data-pipeline-and-bundle-format.md#10-versioning-and-compatibility) keeps minor bumps for additions that readers can ignore. A 1.0 reader would reject a flagged file as corrupt ("Unsupported encoding flags"), not as needing a newer app. Added after a release, they would need schema 2.0. Before the first release they cost nothing, and waiting would also ship demo bundles that miss NFR-04.
   - **Invalid progress samples hold the last valid value**, as X and Y already do. They then cost nothing after delta encoding, and the encoder never meets a NaN. The sizes above assume this; M2's progress must follow it.
3. **Packages:** today's format deflates by under 15 %, which points to stored entries. If decision 2 holds, deflating saves about 61 %, so the rule favours deflated entries. Inflating costs 33–58 ms, well inside NFR-03.
   - **The reader should accept both.** `ZipArchive` reads both with the same code at no extra cost, and the CLI may switch to deflated entries when the format changes, so accepting both keeps older and newer packages readable.
4. **Opening packages: keep `InputFile`.** It meets NFR-03 by a wide margin here, in Chromium and Firefox. `File.arrayBuffer()` through `[JSImport]` is the lever if a laptop gets near 1 s: 100–160 ms faster on a 6 MB package.
5. **Q3:**
   - **`InputFile` and `ZipArchive` work in browser-wasm for 5–10 MB packages:** 335–467 ms to the first frame cold in Chromium and 378–561 ms in Firefox here, stored or deflated, with memory levelling off at 145 MB.
   - **Compressing hosted bundles is worth it only with the format change.** Pages already gzips them; what gets a 2-hour race under 3 MB is delta X/Y and quantised progress (option D).
   - **Brotli for the framework works** with .NET 10 fingerprinted names, and Pages serves the `.br` copies as plain files (S0). Whether it pays off is #37's decision, once your laptop's decode time is in.
